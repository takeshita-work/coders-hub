# 0012: 画面用の書き込み API を、他サイトのページから叩けないように守る

- ステータス: Accepted
- 日付: 2026-10-09

## 背景
MVP の画面側（`127.0.0.1:8766`）は、読み取りだけだった。指示の送信は、セッションへ文章を送り込み、PC 上でコマンドを実行させられる入口になる（`security.md`）。

ブラウザで開いている別のサイトのページから、`http://127.0.0.1:8766/...` へリクエストを送られるおそれがある。

- 別サイトのページからの書き込み（CSRF）
- 利用者のブラウザを経由した、ホスト名の付け替え（DNS リバインディング）

外部公開（REQ-006、ADR 0005）は、この段階では行わない。ローカルの別プロセスが直接叩くことは、利用者自身の権限で動いているため、防ぎきれない前提とする。

## 選択肢
1. 何もしない（ローカルだから安全と見なす）
2. `Host` と `Origin` を検査する
3. 2 に加えて、独自ヘッダーと JSON の `Content-Type` を必須にする
4. 起動のたびに発行するトークンを画面に埋め込み、全リクエストで必須にする

## 決定
3 を採用する。書き込み系の API（`POST` など）は、次をすべて満たすときだけ受け付ける。

- `Host` が `127.0.0.1:<画面ポート>` か `localhost:<画面ポート>`
- `Origin` があるときは、`Host` と同じオリジン
- ヘッダー `X-Coders-Hub: 1` がある
- `Content-Type` が `application/json`

守れなければ 403。CORS の許可ヘッダーは返さない。

## 理由
- 独自ヘッダーと JSON は、他サイトのページからの「単純なリクエスト」にならず、事前確認（プリフライト）が要る。CORS を許可しないので、そこで止まる
- `Host` の検査で、DNS リバインディングも防げる
- トークン（4）は、外部公開のとき（ADR 0005）に認証と合わせて検討する。今は仕組みが増えるわりに、守れる範囲が増えない

## 影響・トレードオフ
- 画面側のクライアントは、書き込みのたびに `X-Coders-Hub: 1` を付ける
- ローカルの別プロセスは、同じ形式で叩けば書き込める。許容する（自分専用、`vision.md`）
- 外部公開するときは、この ADR を `Superseded` にして、認証を前提とした方式にする
- WebSocket は、すでに `Origin` の検査がある。読み取りだけなので、変更しない
