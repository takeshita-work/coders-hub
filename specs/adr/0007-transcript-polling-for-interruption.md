# 0007: 拒否・中断の検知に会話ログ（JSONL）の定期確認を使う

- ステータス: Accepted
- 日付: 2026-10-08（Esc の記録を実機で確認し、Proposed から Accepted に変更）

## 背景
状態の取得はフックで行う（ADR 0003）。しかし、次の操作ではフックの合図が一切来ない。
- 許可プロンプトを**拒否**したとき
- 作業中に **Esc で中断**したとき

公式ドキュメントと実機のログで確認した（`specs/10-requirements/open-questions.md`）。
- `Stop` は「ユーザーによる中断で停止した場合は実行されない」
- `PostToolUseFailure` は権限の拒否で発火せず、実行中のツールのキャンセルでも発火しない
- `PermissionDenied` は auto モードの拒否でのみ発火し、手動の拒否では実行されない

その結果、次の `UserPromptSubmit` まで状態が `permission`／`working` のまま残り、「気づける」（成功の基準 1 位）を損なう。

## 選択肢
1. 割り切る（対処しない。経過時間の表示で気づいてもらう）
2. Channels で補う
3. 会話ログ（JSONL）を定期的に確認して補う
4. 一定時間で「要確認」表示にする
5. 手動で状態を戻すボタンを付ける

## 決定
3 を採用する。各フックの入力にある `transcript_path` の末尾を、**`permission`／`working` のセッションだけ**定期的に確認し、中断・拒否の記録を見つけたら状態を `waiting` に戻す。
- 拒否の記録（実機で確認済み）: `tool_result`（`User rejected tool use`、`is_error`）と、`[Request interrupted by user for tool use]`
- Esc 中断の記録（実機で確認済み）: 許可ダイアログで Esc を押すと、保留中の全ツール呼び出しに `User rejected tool use`（`is_error`）が記録され、続けて `[Request interrupted by user]` が同じ時刻（ミリ秒）に記録された。フックは `SessionEnd` まで何も来なかった
- 検知の文言は、両方に当てはまる前方一致 `[Request interrupted by user` とする
- 未確認: 許可ダイアログのない通常の作業中に Esc を押した場合。同じ文言と推測するが、実装後の実機確認（tasks T6-2）で確かめる。外れた場合は、状態が戻らないだけ（現状と同じ）
- 状態の取得は引き続きフックが主で、JSONL は**状態を戻す補助**に限る（ADR 0003 の方針を維持する）

## 理由
- 拒否は、約 1.8 秒後にログへ記録されていた（`PermissionRequest` の 39:14.9 に対し 39:16.68）。1 秒間隔の確認で、NFR-003（3 秒以内）に収まる見込み
- 確認の対象は `permission`／`working` のセッションに限る。`waiting` は確認しない。30 セッションでも、末尾だけ読めば負荷は小さい
- Channels は、解決済み・中断を知らせる通知が公式ドキュメントになく、解決にならない（開発用フラグも必要になる）
- 手動ボタンや「要確認」表示は、誤検知や手間がある。気づける、という目的に合わない

## 影響・トレードオフ
- JSONL は内部フォーマットで、バージョンアップで変わりうる（NFR-008）。変わって検知できなくなっても、状態が戻らないだけ（現状と同じ）で済むよう、補助用途に限定する
- 検知の遅延は、確認間隔（1 秒を想定）＋ログの書き込み遅延
- ログの末尾を読む処理が必要になる。REQ-007（直近の会話の参照）でも同じ読み取りを使えるため、共通の部品にできる
- 確認の間隔、読む範囲（末尾何バイト・何行）、検知する文言のパターンは plan で詰める
- `transcript_path` は Windows のパスで渡される。パスの扱いを確認する
