# specs

Coders Hub の仕様。ここを唯一の正とし、コードは仕様に従う。

## 構成

| ディレクトリ | 内容 | 変更頻度 |
|---|---|---|
| `00-product/` | なぜ作るか（ビジョン・用語・競合） | ほぼなし |
| `10-requirements/` | 何ができるべきか（機能・非機能要件、未解決の論点） | 低 |
| `20-design/` | 全体としてどう作るか（構成・状態モデル・API・セキュリティ） | 中 |
| `30-features/` | 機能単位の spec / plan / tasks（開発の作業単位） | 高 |
| `adr/` | 設計判断の記録（追記のみ） | 追記のみ |

## ステータス

| ステータス | 意味 |
|---|---|
| Draft | 下書き。未合意 |
| Approved | 合意済み。実装してよい |
| Implemented | 実装・テスト済み |
| Deprecated | 廃止（削除せず理由を残す） |

## ID 規則
- 要件: `REQ-001`（機能）、`NFR-001`（非機能）
- 受け入れ条件: `AC-001-1`（REQ-001 の 1 番目）。テストから参照する
- ADR: `0001-xxx.md`（連番）

## 仕様変更の手順
1. 先に spec（必要なら plan / tasks）を更新する
2. 方式変更・重要な判断は ADR を追加（既存 ADR は書き換えず `Superseded by` にする）
3. 実装・テストを更新する
4. spec・ADR・コードを同じ変更にまとめる

| 変更の大きさ | 扱い |
|---|---|
| 軽微（文言・表示項目） | spec を直接更新 |
| 中（挙動の変更） | spec と plan を更新し、tasks を作り直す |
| 大（方式・スコープの変更） | ADR を追加し、関連 spec を一括更新 |

## 進め方
最初から全部は埋めない。`00-product` → `10-requirements` → `adr` の順に固め、MVP の範囲が決まったら `20-design` と `30-features` を詰める。
