# 002 指示の送信

- ステータス: Draft（合意前）
- 対応要件: REQ-002, REQ-003, REQ-005
- 関連 NFR: NFR-003, NFR-009
- 関連 ADR: 0001（指示の送信に Channels）、0011（操作モード）、0012（画面用の書き込み API の保護）
- 前提の実機確認: Windows のターミナル版で、アイドル中・作業中とも指示を送れた（ADR 0001、2026-10-09）

## 目的
ダッシュボードから、動いているセッションへ指示（文章）を送れるようにする。ターミナルまで戻らずに、返答待ちのセッションを次の作業へ進められる（成功の基準「操作できる」の最初の一歩）。

## 用語
`../../00-product/glossary.md` に従う。「操作モード」は、チャネルサーバーを `--channel` 付けで起動し、`claude` に開発用フラグを渡して起動したセッション（ADR 0011）。

## 振る舞い

### 指示を送れるセッション
- 操作モードのチャネルサーバーが接続しているセッションだけが、指示を送れる
- 一覧の行に、そのセッションが操作できるかどうかが分かる表示がある
- 操作できないセッション（一覧だけのモード）では、送信の操作ができず、理由（「操作モードで起動していません」）が分かる

### 指示の送信
- 一覧の行から、指示を入力して送信できる（複数行・日本語可）
- 空（空白だけ）の指示は送れない。上限は 10,000 文字
- 返答待ちのセッションに送ると、セッションはそれを通常のユーザー入力として受け取り、作業を始める。時間がたってからでも送れる（REQ-002）
- 作業中のセッションに送った指示は、取りこぼされず、現在の処理が終わったあとに処理される（REQ-003）
- 許可待ち・質問待ちのセッションにも送れる。ただし、許可や回答が先に必要なことが画面に示される（処理されるタイミングは「未決事項」）
- 続けて複数の指示を送ったときは、送った順に処理される
- 指示は、ターミナルにも「チャネルから来た入力」として表示される

### 送信の結果
画面に、送った指示ごとの結果を表示する。

| 結果 | 意味 |
|---|---|
| 送信中 | Hub 本体がセッションへ渡す前 |
| 届きました | セッションの会話ログに、指示の記録が確認できた |
| 届いたか確認できません | 一定時間（15 秒）たっても、確認できない |
| 送れませんでした | セッションが存在しない・操作モードでない・入力が不正など。理由を表示する |

- 「届いたか確認できません」は、フラグの付け忘れ（通知が黙って捨てられる）や Hub 本体の再起動で起こる。再送するかどうかは、利用者が決める（自動の再送はしない）
- 結果の表示は、その画面を開いている間だけ。再読み込みで消える

### ターミナルとの共存（REQ-005）
- アプリから指示を送れる状態でも、ターミナルでの入力は通常どおりできる
- アプリからの指示とターミナルの入力が重なっても、どちらも取りこぼされない（`claude` 側のキューに入り、順に処理される）

### 保存しない（NFR-009）
- 送った指示の本文は、セッションへ渡したあと、Hub 本体のメモリに残さない
- 指示の履歴は、画面にも保存しない

### 安全面（ADR 0012）
- 指示の送信は、他のサイトのページからは行えない
- 外部公開はしない（REQ-006 は別の機能）

## 受け入れ条件

### 送信（REQ-002）
- AC-002-1: 操作モードのセッションの行から、指示を入力して送信できる
- AC-002-2: 返答待ちのセッションに指示を送ると、セッションが作業を始める（状態が作業中になる）。10 分以上たってからでも同じである
- AC-002-3: 改行・日本語・記号（引用符・バックスラッシュ・`<`）を含む指示が、そのままの本文でセッションへ渡る
- AC-002-4: 空の指示、10,000 文字を超える指示は送れない（画面で入力できない、または理由が表示される）
- AC-002-5: 操作モードでないセッションでは、送信の操作ができず、理由が表示される

### 結果の表示
- AC-002-6: 送信の結果（送信中／届きました／届いたか確認できません／送れませんでした）が、指示ごとに画面で分かる
- AC-002-7: 届いた場合、送信から 3 秒以内に「届きました」になる（NFR-003 に準じる）
- AC-002-8: 通知が届かない場合（開発用フラグなし、Hub 本体の再起動など）、15 秒後に「届いたか確認できません」になる。画面が黙ったままにならない
- AC-002-9: 存在しないセッション、終了したセッションへの送信は、「送れませんでした」になる

### 作業中・複数の指示（REQ-003）
- AC-003-1: 作業中のセッションに送った指示は、取りこぼされず、現在の処理が終わったあとに処理される
- AC-003-2: 続けて送った複数の指示が、送った順に処理される

### 共存（REQ-005）
- AC-005-1: アプリから指示を送れる状態で、ターミナルから入力しても、通常どおり処理される
- AC-005-2: アプリから送った指示が、ターミナルにも表示される（チャネルから来た入力と分かる）

### 保存・安全
- AC-002-10: 指示の本文は、セッションへ渡した後に Hub 本体のメモリに残らない（NFR-009）
- AC-002-11: 他のオリジンのページ、不正な `Host`、独自ヘッダーなしのリクエストでは、指示を送れない（403。ADR 0012）

## 対象外
- 許可プロンプトへの応答（REQ-004 → `003-permission-relay`）
- 質問（`AskUserQuestion`）への回答の選択（質問待ちには文章の指示だけを送れる）
- 会話内容の参照（REQ-007）。送った指示への応答も、画面には出さない
- 指示の履歴・下書きの保存、テンプレート
- 自動の再送、予約送信、複数のセッションへの一斉送信
- 画像・ファイルの添付
- 外部からの利用・認証（REQ-006）、スマホ表示
- `asyncRewake` の Stop フックによる代替経路（Channels が使えない場合の代替。必要になったら別の機能にする）

## 未決事項
- 許可待ち・質問待ちのセッションに送った指示が、いつ処理されるか（ダイアログの前か後か）。実機で確認して、画面の案内を決める
- 「届きました」を確認する方法。会話ログに、チャネルからの入力の記録が残る（`origin.kind: channel`、`queue-operation`）。通知の `meta` を、記録から読み取れる形で付けられるか確認する（plan の検証 2）
- チャネル機能を宣言したサーバーを、開発用フラグなしで起動したときの挙動（エラーか、警告か、黙って無効か）。無効なことを `/poll` の時点で知る方法があるか
- 操作モードのセッションの行で、入力欄を常に出すか、ボタンで開くか（画面で決める）
