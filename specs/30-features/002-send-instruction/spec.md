# 002 指示の送信

- ステータス: Implemented（2026-10-09。自動テスト 234 件、実機の確認は `./acceptance.md`）
- 対応要件: REQ-002, REQ-003, REQ-005
- 関連 NFR: NFR-003, NFR-009
- 関連 ADR: 0001（指示の送信に Channels）、0011（操作モード）、0012（画面用の書き込み API の保護）、0013（保留して返答待ちで渡す）
- 前提の実機確認: Windows のターミナル版で、返答待ち（アイドル）のセッションへ指示を送れた（ADR 0001）。作業中の通知は指示として扱われない（ADR 0013）

## 目的
ダッシュボードから、動いているセッションへ指示（文章）を送れるようにする。ターミナルまで戻らずに、返答待ちのセッションを次の作業へ進められる（成功の基準「操作できる」の最初の一歩）。

## 用語
`../../00-product/glossary.md` に従う。「操作モード」は、チャネルサーバーを `--channel` 付けで起動し、`claude` に開発用フラグを渡して起動したセッション（ADR 0011）。「保留」は、Hub 本体が指示を預かり、セッションが返答待ちになるまで渡さないこと（ADR 0013）。

## 振る舞い

### 指示を送れるセッション
- 操作モードのチャネルサーバーが接続しているセッションだけが、指示を送れる
- 一覧の行に、そのセッションが操作できるかどうかが分かる表示がある
- 操作できないセッション（一覧だけのモード）では、送信の操作ができず、理由（「操作モードで起動していません」）が分かる

### 指示の送信
- 一覧の行から、指示を入力して送信できる（複数行・日本語可）
- 空（空白だけ）の指示は送れない。上限は 10,000 文字
- 返答待ちのセッションに送ると、すぐにセッションへ渡され、通常のユーザー入力として処理される。時間がたってからでも送れる（REQ-002）
- 作業中・許可待ち・質問待ちのセッションに送った指示は、Hub 本体が**保留**する。セッションが返答待ちになったときに渡される（REQ-003）
- 保留中の指示は、一覧の行に表示され、渡される前なら取り消せる
- 保留中の指示が複数あるときは、送った順に、**1 件ずつ**渡される。次の指示は、前の指示の処理が終わって、再び返答待ちになってから渡される
- 本文の中の `</channel>` は、`<\/channel>` に置き換わってセッションに届く（`claude` 側の仕様。ほかの文字は変わらない）

### 送信の結果
画面に、送った指示ごとの結果を表示する。

| 結果 | 意味 |
|---|---|
| 保留中 | Hub 本体が預かっている。セッションが返答待ちになるのを待っている |
| 送信中 | セッションへ渡した。会話ログで確認するまで |
| 届きました | セッションの会話ログに、指示として処理された記録が確認できた |
| 指示として扱われませんでした | 届いたが、作業中に重なったため、参考情報として扱われた（再送するかは利用者が決める） |
| 届いたか確認できません | 渡してから一定時間（15 秒）たっても、確認できない |
| 取り消しました | 保留中に、利用者が取り消した |
| 失われました | Hub 本体の再起動などで、保留中の指示が消えた |
| 送れませんでした | セッションが存在しない・操作モードでない・入力が不正など。理由を表示する |

- 「届いたか確認できません」は、開発用フラグの付け忘れ（通知が黙って捨てられる。実機で確認済み）などで起こる。再送するかどうかは、利用者が決める（自動の再送はしない）
- 結果の表示は、その画面を開いている間だけ。再読み込みで消える（保留中の指示は、Hub 本体が持っているので、再読み込み後も表示される）

### ターミナルとの共存（REQ-005）
- アプリから指示を送れる状態でも、ターミナルでの入力は通常どおりできる
- アプリからの指示は、ターミナルにも「チャネルから来た入力」として表示される
- 利用者がターミナルで入力を始めたのと、指示を渡すタイミングが重なった場合は、「指示として扱われませんでした」として画面で分かる

### 保存しない（NFR-009）
- 保留中の指示の本文だけが、Hub 本体のメモリにある。セッションへ渡した時点で、本文を破棄する
- 指示の履歴は、Hub 本体にも画面にも保存しない

### 安全面（ADR 0012）
- 指示の送信と取り消しは、他のサイトのページからは行えない
- 外部公開はしない（REQ-006 は別の機能）

## 受け入れ条件

### 送信（REQ-002）
- AC-002-1: 操作モードのセッションの行から、指示を入力して送信できる
- AC-002-2: 返答待ちのセッションに指示を送ると、セッションが作業を始める（状態が作業中になる）。10 分以上たってからでも同じである
- AC-002-3: 改行・日本語・記号（引用符・バックスラッシュ・`<`・`&`）を含む指示が、そのままの本文でセッションへ渡る（`</channel>` だけは `<\/channel>` になる）
- AC-002-4: 空の指示、10,000 文字を超える指示は送れない（画面で入力できない、または理由が表示される）
- AC-002-5: 操作モードでないセッションでは、送信の操作ができず、理由が表示される

### 結果の表示
- AC-002-6: 送信の結果（保留中／送信中／届きました／指示として扱われませんでした／届いたか確認できません／取り消しました／失われました／送れませんでした）が、指示ごとに画面で分かる
- AC-002-7: 返答待ちのセッションに送った場合、送信から 3 秒以内に「届きました」になる（NFR-003 に準じる）
- AC-002-8: 通知が届かない場合（開発用フラグなし、Hub 本体の再起動など）、渡してから 15 秒後に「届いたか確認できません」になる。画面が黙ったままにならない
- AC-002-9: 存在しないセッション、終了したセッションへの送信は、「送れませんでした」になる

### 保留・順序（REQ-003）
- AC-003-1: 作業中・許可待ち・質問待ちのセッションに送った指示は、保留中になり、セッションが返答待ちになったときに渡されて、ユーザーの指示として処理される
- AC-003-2: 保留中の指示が複数あるとき、送った順に 1 件ずつ渡される。前の指示の処理が終わるまで、次は渡されない
- AC-003-3: 保留中の指示は、一覧の行に表示され、渡される前に取り消せる。取り消した指示は渡されない
- AC-003-4: 保留中のセッションが閉じられたら、その指示は破棄され、「失われました」と分かる
- AC-003-5: Hub 本体を再起動して保留中の指示が消えたとき、再接続した画面が「失われました」と表示する。黙って「保留中」のままにならない

### 共存（REQ-005）
- AC-005-1: アプリから指示を送れる状態で、ターミナルから入力しても、通常どおり処理される
- AC-005-2: アプリから送った指示が、ターミナルにも表示される（チャネルから来た入力と分かる）
- AC-005-3: 指示を渡すタイミングが作業と重なり、注意書きとして扱われた場合、「指示として扱われませんでした」と分かる

### 保存・安全
- AC-002-10: 指示の本文は、セッションへ渡した後に Hub 本体のメモリに残らない（NFR-009）
- AC-002-11: 他のオリジンのページ、不正な `Host`、独自ヘッダーなしのリクエストでは、指示を送れない・取り消せない（403。ADR 0012）

## 対象外
- 許可プロンプトへの応答（REQ-004 → `003-permission-relay`）
- 質問（`AskUserQuestion`）への回答の選択（質問待ちには、文章の指示を保留として送るだけ）
- 会話内容の参照（REQ-007）。送った指示への応答も、画面には出さない
- 指示の履歴・下書きの保存、テンプレート、保留中の指示の編集（取り消して送り直す）
- 自動の再送、予約送信、複数のセッションへの一斉送信
- 画像・ファイルの添付
- 外部からの利用・認証（REQ-006）、スマホ表示
- `asyncRewake` の Stop フックによる代替経路（必要になったら別の機能にする）
- 作業中のセッションへの割り込み（作業中に送った指示は、作業が終わってから届く）
